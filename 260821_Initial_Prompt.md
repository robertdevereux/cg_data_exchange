## A. Environment and commands

**Repo:** github.com/robertdevereux/cg_data_exchange (private)

**Claude Code:** launch from project root with:
```
claude --dangerously-skip-permissions
```

**If you get a 401 auth error:** exit CC, then:
```
set -a; source .env; set +a
claude /logout
claude --dangerously-skip-permissions
```
The auth conflict arises when both a claude.ai token and `ANTHROPIC_API_KEY` are set.
`/logout` clears the claude.ai token; the API key then takes sole control.

**Test command** (always use this exact form):
```
/Users/robert/anaconda3/envs/env_python_django_psql/bin/python manage.py test --keepdb
```
Never use `python manage.py test`, `source activate`, or `conda run`.
Correct conda environment is `env_python_django_psql` (with `_psql` suffix).

Never run two manage.py test invocations against the Neon test DB concurrently. Sequential only. Several test classes (TestRoutingAdminTools, TestConditionalTableSection, likely others) use fixed-ID fixtures in setUpTestData and will fail with spurious unique-constraint errors under concurrent execution — this is a known, understood test-infrastructure limitation, not a code bug.

**`--keepdb` runs against `test_<DB_NAME>`, not the live database.** Django's
test runner creates and reuses a separate database on the same Neon server;
`--keepdb` just skips dropping/recreating it between runs. Direct SQL run
against the live DB (see below) is invisible to the test suite, and vice
versa — the two are fully isolated. Confirmed 19 August 2026 while
diagnosing an apparently-related test failure that turned out to be
pre-existing and unconnected.

**Load environment variables locally:**
```
set -a; source .env; set +a
```
The `.env` file must not have spaces in values. `ALLOWED_HOSTS` uses
comma separation, not space separation.

**Local runserver** hits the production Neon database (not SQLite).
Run `manage.py load_test_data` locally to update production data without
a Render deploy.

**Direct SQL against the live Neon DB** (e.g. authoring routing rows by
hand — see `260815_Ownership_fork_routing_template.md` for the pattern):
if working in Neon's own web SQL editor rather than a persistent `psql`
terminal session, **do not split `BEGIN;` / `INSERT` / verification
`SELECT`s / `COMMIT;` across separate "Run" actions.** The web editor does
not reliably hold one session open between clicks — a transaction left
open while you go and check the output separately can silently time out
and roll back before you come back to commit it (this happened once, 18
August 2026, and cost an already-verified insert). Either paste and run
the entire `BEGIN` → `INSERT` → verify → `COMMIT` block as a single
execution, or, if you need to pause between inserting and reviewing,
`COMMIT` as soon as the row count is confirmed and treat the detailed
review as an ordinary read afterwards — accepting the loss of the
"rollback if it looks wrong" safety net as the trade-off.

**file_dump.txt** is generated by `combine_files_claude.py` in the project
root. It includes all `.py` and `.html` files. It is gitignored — a Claude
working document, not source code. Always regenerate from the current
codebase before starting Claude Code work, and again after any Claude Code
session that touches `.py`/`.html` files before the next chat relies on it
— a stale dump has already caused at least one wasted diagnostic pass
(15–16 August 2026, `SectionQuestionGuidance` work) where a genuinely
fixed issue looked unconfirmed simply because the dump predated the fix.

**`.claude/` directory** is gitignored. Claude Code worktrees must never
be committed to the repo.

**Session commit rule (standing):** Commit to git at the end of every
verified, test-passing session — before starting the next session, and
*especially* before any worktree is created for a subsequent task.
A worktree always branches from the last commit, never from uncommitted
working-tree state. Uncommitted changes present in main when a worktree
is created will be invisible to that worktree; copying the worktree back
to main will silently overwrite them. The canonical close-out sequence is:
run full test suite → confirm zero failures → `git add` relevant files →
`git commit` → then hand off to the next session. **Note: this covers git-
tracked code changes only.** Direct SQL changes to live routing/question
data (see above) aren't captured by a git commit — record those in the
Backlog's Completed log instead, as has been done for the HMRC_S8 and
HMRC_S7 routing builds.

**Database note:** The user table is `core_user` (not `auth_user`).
Example: `SELECT id FROM core_user WHERE username = 'alice';`

**Render:** Two active services (DEMO and HMRC), both from the same repo,
differentiated by env vars set in the Render dashboard:
```
https://cg-data-exchange.onrender.com         (DEMO/TEST)
https://cg-data-exchange-hmrc.onrender.com    (HMRC)
```

## B. Project structure and the core/dept split

The project is a Django 5.1 PoC called `cg_data_exchange`, demonstrating
a new operating model for citizen-government data exchange.

### The fundamental split

**`core`** is the platform. It owns:
- The platform data model (all platform models live here)
- The execution engine — everything that happens inside a section:
  question rendering, answer capture, routing, confirmation, audit trail
- The platform interface (`core/interfaces.py`) — the documented contract
  that dept apps call
- Shared admin tooling for configuration

**Department apps** (`dept_hmrc`, `dept_demo`)
own their orchestration logic, home page UX, and any dept-specific models.
They call into core via `interfaces.py`. They never query core models
directly. `dept_hmrc` has `models.py` with `IHTReckoner` — the canonical
pattern for dept-specific data that falls outside core_answer.

The execution engine is invariant — dept apps do not modify it. Adding a
new department means writing a new dept app; the platform requires no changes.

### Project folder structure

```
config/               — Django project config (settings, urls, routers)
core/                 — Platform app (data model + execution engine)
  models.py           — All models (includes SectionQuestionGuidance —
                        per-section override of a shared Question's
                        guidance/hint text; see Core Platform Reference)
  interfaces.py       — Platform interface for dept apps
  views_layer2.py     — Execution engine (section journey)
  views_layer1.py     — Shared navigation views (regime_top_level,
                        regime_schedules, regime_schedule_sections,
                        regime_sections)
  views_admin_tools.py — Admin tooling
  templatetags/       — Markdown rendering
core/templates/core/  — All execution engine and admin templates
dept_hmrc/            — HMRC department app
dept_demo/            — Demo/test dept (internal dept_id='TEST', /demo/ prefix)
```

### dept_hmrc folder structure (canonical pattern for new depts)

```
dept_hmrc/
  models.py           — IHTReckoner (dept-specific model, outside core_answer)
  urls.py
  apps.py
  tests.py
  views/
    __init__.py         — re-exports for urls.py
    hmrc_home.py        — dept_home, regime_list, regime_home (thin dispatcher)
    iht/
      __init__.py
      orchestrate.py    — iht_orchestrate (two-phase dispatcher) + action button
                          views + entry/exit functions + home page builders
      screen.py         — iht_screen, iht_screen_unverified, _decorate_actions
                          (presentation only — never reads DB)
      matching.py       — run_iht_matching, _generate_iht_reference (functions only)
      reckoner.py       — handle_reckoner, get_reckoner_state,
                          iht_reckoner_compute, iht_reckoner_threshold
      utils.py          — _get_iht_answers shared helper
  templates/dept_hmrc/
    dept_home.html
    regime_home.html
    iht/
      home.html         — IHT estate homepage
      duplicate.html    — Duplicate case page (first-time matching conflict)
```

Adding a new tax regime to HMRC: new `elif` in `regime_home` + new subfolder
under `views/`. Each major action item on the home page gets its own `.py` file.

Adding a new department: follow `dept_hmrc` as the canonical pattern.
See `260528_Setting_Up_a_New_Department_v2.docx` for the process.

### Key architectural patterns

**Two-phase action button pattern (HMRC IHT)**
Every action button has an ENTRY and EXIT in `iht_orchestrate`.
Two session flags drive dispatch:
- `iht_in_core` — True while user is inside core; set on entry, popped on
  every regime home visit to distinguish entry from exit
- `iht_current_action` — which action button is active

`call_core` sets `return_url = regime_home_url` so core always returns
to the dept orchestrator. No `post_confirm_redirect` used in HMRC IHT.
See HMRC IHT Reference section 2 for full detail.

**Orchestrate / screen separation**
`orchestrate.py` reads state and dispatches — never renders.
`screen.py` renders — never reads DB. `_build_action_list` returns lean
logical state (no labels/colours); `_decorate_actions` in screen.py adds
presentation.

**Ownership-fork routing block (IHT asset sections)**
A reusable set of routing questions (HMRC_46/48/49/50/51/52/55/54/61/62)
capturing sole/joint/tenants-in-common ownership and, where relevant, how
much of the deceased's share passes to a surviving spouse. Built once for
HMRC_S8 (property) and reused by ID — unchanged — for HMRC_S7 (bank
accounts); intended to be reused again for any future asset-class section
in the same shape. Two things are asset-class-specific and vary per
section: (1) what precedes the fork (property chains three individual
questions; bank accounts use a single `SET11` page) and (2) what follows
it, if anything (property has a substitute-valuation-evidence tail via
`HMRC_60`; bank accounts end immediately). Guidance/hint text that needs
to vary by asset class (e.g. "not sure how this is owned?" pointing to the
Land Registry for property vs. account statements for bank accounts) is
handled via `SectionQuestionGuidance`, not by forking the questions
themselves — see `260815_Ownership_fork_routing_template.md` for the full
pattern and reuse checklist.
